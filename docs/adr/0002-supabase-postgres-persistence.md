# ADR 0002: Persistence for signals and events (Supabase Postgres via a direct driver)

- Status: Accepted (Phase 2 plan approved by the project owner, who chose Supabase)
- Date: 2026-10-24

## Context

Phase 2 must persist ingested signals, their processing outcomes and the Live Activity events
(`AGENTS.md` sections 4, 11, 15). The signal row and the events that describe it must commit or fail
together, concurrent identical submissions must not both become canonical, and events must be append-only.
The project owner wants Supabase as the database. Supabase is hosted PostgreSQL, which matches the
`AGENTS.md` preference for a relational database.

The application server is the only database client. Phase 5 sign-in is an application session cookie (ADR 0003), not Supabase Auth.

## Options

1. **SQLite file.** Zero setup, but the owner chose Supabase and a file DB does not carry over to a hosted
   multi-instance deployment.
2. **`supabase-js` (PostgREST) from the server.** Official client, but each call is a separate HTTP request:
   no multi-statement transaction, so "signal + events commit together" and advisory locking are not
   possible. It would also push us toward anon/service-role keys inside the app.
3. **In-memory only.** Fine for tests, but not persistence. Kept as a test implementation and as an explicit,
   labelled development mode, never as a silent fallback.
4. **Supabase Postgres through a direct driver (`postgres`, porsager) with a server-only `DATABASE_URL`.**
   Real transactions, parameterized queries, plain SQL migrations, same SQL on any Postgres.

## Decision

Option 4, behind a repository interface (`SignalRepository`) with an in-memory implementation and a
Postgres implementation that share one contract test suite.

- Connection: a server-only `DATABASE_URL`. The Supabase **Session pooler** connection string is recommended
  because the direct connection is IPv6-only. The client sets `prepare: false` so the transaction pooler also
  works. No Supabase anon key or service-role key is used or required by the app.
- Schema: plain SQL under `supabase/migrations/`, applied by `npm run db:migrate` with our own idempotent
  ledger table `app_migrations`. We do not require the Supabase CLI.
- **RLS:** every table has row level security enabled with no policies, and all privileges are revoked from
  `anon` and `authenticated`. Supabase exposes `public` tables through its REST API by default; this keeps
  that API from reading or writing our data even if a key leaks. The app connects as the owner role and
  bypasses RLS, so **tenant isolation is enforced in the repository layer** (every method takes `tenantId`)
  and proven by tests, not by RLS.
- Events are append-only, enforced by a database trigger (update/delete/truncate raise).
- Concurrency: a transaction-scoped advisory lock on the dedupe key serializes identical submissions; a
  partial unique index on canonical signals with a source record id is the backstop.
- Timestamps on events are generated by the server, never taken from the client.
- The Postgres repository talks to a minimal `SqlClient` interface (`query(text, params)` + `transaction`).
  Production uses the `postgres` driver. Tests additionally run the **same SQL and migrations** against
  PGlite (in-process Postgres compiled to WASM), so the SQL is exercised without credentials or Docker.
  PGlite is a **dev dependency only**.
- A `TEST_DATABASE_URL` can additionally point the contract suite at a throwaway Supabase schema.

Dependencies added:

- `postgres`: the driver.
- `server-only`: makes importing database/env code from a client component a build error.
- `tsx` (dev): runs `db:migrate` and `db:seed` scripts.
- `@electric-sql/pglite` (dev): real-Postgres semantics in tests.

## Consequences

- A Supabase project and a `DATABASE_URL` are prerequisites for the database mode. Without them the app
  runs on fixtures (`DATA_SOURCE=fixtures`, the default) or on the explicit in-memory development mode.
- With `DATA_SOURCE=database` and an unreachable database the UI shows an explicit error state. It never
  falls back to fixtures.
- Using only the database connection string means no Supabase Auth/Storage/Realtime features are used.
  Phase 5 sign-in is the signed cookie in ADR 0003. The later SSE phase will revisit live delivery.
- Because the app role bypasses RLS, a bug in the repository layer could leak across tenants. Mitigations:
  tenant id is a required argument of every repository method, the contract suite asserts cross-tenant
  reads return nothing, and `docs/signal-ingestion.md` documents that the ingest key maps to one tenant.
- The repository interface is async and transactional; replacing Supabase later means a new
  implementation of one interface.

## Revisit criteria

- Multiple application roles or end-user database access: add real RLS policies and per-user JWT claims.
- Sustained ingest volume beyond a single pooled connection set: re-evaluate pooling and queueing.
- A requirement for push delivery to browsers: SSE phase decides whether to use Postgres notifications.
